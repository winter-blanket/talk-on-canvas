# 대화 캔버스 (`/talk-on-canvas`)

터미널 출력은 길어지면 읽히지 않는다. 표는 깨지고, 코드와 산문이 섞이고, 10분 전에 합의한 내용은 스크롤백 저 위로 사라진다. 이 스킬은 **브라우저에 띄워 둔 HTML 한 장**을 대화와 같은 속도로 갱신해, 사용자가 그 화면을 보면서 터미널과 대화하게 만든다.

study-on-canvas 가 "개념 학습"이라는 고정된 목적과 고정된 화면을 가진 것과 달리, 이 스킬은 **내용 구조가 정해져 있지 않다.** 설계 논의면 설계 표가, 디버깅이면 가설·증거 목록이, 기획이면 화면 흐름이 들어간다. 매 턴 "이 대화를 읽기 좋게 만들려면 지금 어떤 블록이 필요한가"를 판단하는 게 이 스킬의 일이다.

## 발동 조건

`/talk-on-canvas` 슬래시 명령으로만 발동한다. 자연어 호출은 지원하지 않는다.

"정리해줘", "HTML로 뽑아줘" 는 일회성 파일 요청이지 대화 캔버스가 아니다. 그 요청에 이 스킬이 끼어들면 서버를 띄우고 세션 내내 갱신 의무를 지는, 사용자가 원하지 않은 모드로 들어간다. 진입점을 슬래시 명령 하나로 좁혀 둔다.

캔버스가 이미 열려 있는 동안에는 재발동하지 않는다. 사용자가 다시 `/talk-on-canvas` 를 쳐도 새 파일을 만들지 말고, 열려 있는 캔버스의 제목을 새 주제로 바꾸고 섹션을 이어 쌓는다. 새 파일은 사용자가 "새 캔버스로" 라고 명시할 때만 만든다.

## 산출물 형태 — 로컬 파일 기본

캔버스는 **로컬 HTML 파일로 만든다.** Artifact 로 발행하지 않는 것이 기본값이다.

이 스킬의 값어치는 전부 갱신 속도에서 나온다. 로컬 서버가 1.2초마다 변경을 감지해, 사용자는 터미널에 말하는 동안 옆 화면이 따라오는 것을 본다. Artifact 는 매 턴 재발행이 필요하고 그만큼 늦어서, "대화 속도로 따라오는 화면"이라는 전제가 깨진다. 거기에 캔버스는 파일 경로·코드 조각·디버깅 로그처럼 바깥에 올리기 곤란한 작업 내용을 그대로 담는다.

짝 스킬인 `/study-on-canvas` 는 반대로 **Artifact 가 기본값**이다. 학습 노트는 세션이 끝난 뒤 다시 꺼내 보는 결과물이라 URL 로 남는 쪽이 맞고, 갱신도 개념 단위라 재발행 간격이 길다. 두 스킬의 기본값이 갈리는 이유는 갱신 주기이지 취향이 아니다.

**Artifact 로 올리는 경우는 사용자가 그러자고 할 때뿐이다.** 보통 세션 끝에 "이거 공유하고 싶다" 로 온다. 그때도 캔버스 자체는 계속 로컬로 굴리고, 발행용 사본을 따로 떠서 그것만 올린다.

```bash
sed -E '/^(<!DOCTYPE html>|<html lang=|<\/html>|<head>|<\/head>|<body>|<\/body>)/d' "$CANVAS" > "${CANVAS%.html}.artifact.html"
```

템플릿은 완전한 HTML 문서라서 껍데기를 벗기지 않으면 Artifact 래퍼 안에 중첩된다. 발행본에서는 자동 갱신 폴링과 `data-rev` 루프가 동작하지 않으므로, 그 시점의 스냅샷이라는 점을 사용자에게 알린다. 이후 대화로 캔버스가 바뀌면 같은 파일 경로로 다시 발행해야 링크 내용이 따라온다.

## 핵심 원칙 (반드시 지킬 것)

1. **캔버스 갱신 없이 턴을 끝내지 않는다.** 내용이 있는 답변을 한 턴은 반드시 Edit + rev 증가로 끝난다. 예외는 아래 "턴 종료 조건" 의 세 가지뿐.
2. **캔버스는 대화 로그가 아니라 현재 상태다.** 같은 주제를 또 다루면 새 섹션을 쌓지 말고 그 섹션을 고쳐 쓴다. 캔버스는 길이로 자라지 않고 정확도로 자란다.
3. **터미널에 내용을 쓰지 않는다. 전부 캔버스로 간다.** 사용자는 캔버스만 본다 — 터미널은 프롬프트를 입력하는 자리다. 자세한 규칙은 아래 "터미널에 무엇을 쓰는가".
4. **파일 전체 재작성 금지.** 모든 편집은 마커 사이 Edit 으로만 한다.
5. **rev 는 갱신의 일부다.** `<html data-rev>` 를 올리지 않으면 브라우저는 아무것도 모른다. 올리지 않은 갱신은 갱신이 아니다.
6. **사용자가 지목하지 않은 다음 행동을 캔버스에 단정해 쓰지 않는다.** 추측은 `열린 질문` 칸에 질문으로 적는다.
7. **묻지 않은 발행을 하지 않는다.** 캔버스는 로컬 파일이 기본이다. Artifact 는 사용자가 공유하겠다고 말했을 때만 — 위 "산출물 형태" 참조.

## 화면 구조 — 탭 3개

캔버스는 상단 바(제목·일시정지·맨 위로) 아래 **탭 3개**로 나뉜다. 어느 내용을 어디에 쓸지는 이 구조가 정한다.

| 탭 | 담는 것 | 마커 |
| --- | --- | --- |
| **한 눈에 보기** | 지금 하는 일 · 다음 · 정해진 것 · 열린 질문 | `<!-- ST:* -->` |
| **할 일 목록** | 사용자가 직접 해야 하는 행동만 | `<!-- TODO -->` |
| **본문** | 설명·표·코드·비교 등 섹션 전부. 좌측 목차는 **이 탭에만** 있다 | `<!-- SECTIONS_INSERT -->` |

빈 탭은 흐려지고, 안쪽에 "아직 없습니다" 안내가 뜬다.

### 숨은 탭에 생긴 변화는 탭 버튼이 알린다

사용자는 한 번에 한 탭만 본다. 그래서 보고 있지 않은 탭의 내용이 바뀌면 그 탭 버튼에 점이 붙고, `할 일 목록` 탭에는 `3/7` 처럼 완료 개수가 함께 뜬다. 탭을 열면 표시가 사라진다.

**이 때문에 터미널 포인터에는 탭 이름을 넣는다.** "할 일 목록에 2개 추가" 가 "2개 추가" 보다 쓸모 있는 이유다 — 사용자가 어느 탭을 열어야 할지 바로 안다.

## 터미널에 무엇을 쓰는가

**사용자는 캔버스만 본다.** 터미널은 프롬프트를 입력하는 자리이고, 읽는 자리가 아니다. 이 전제가 깨지는 순간 사용자는 화면 두 개를 번갈아 보며 어느 쪽이 최신인지 맞춰야 하고, 그러면 이 스킬을 쓰는 이유가 사라진다.

### 쓸 수 있는 것 — 가리키는 말뿐

터미널 답변은 **어디를 보라는 포인터 2~4줄**이다. 고친 자리의 이름을 부르는 것까지만 한다.

```
할 일 목록에 2개 추가했습니다. 채널 섹션의 링크 방향 표를 고쳤습니다.
```

### 절대 쓰지 않는 것

- **캔버스에 없는 사실.** 결론·근거·수치·권고·할 일 — 하나라도 터미널에만 있으면 규칙 위반이다
- **캔버스 내용의 요약·재진술.** 짧게 줄여 쓰는 것도 두 번 쓰는 것이다. 사용자가 캔버스에서 읽을 내용을 터미널에서 미리 읽게 만들지 않는다
- **사용자에게 던지는 질문.** 질문은 `한 눈에 보기` 탭의 `열린 질문` 칸에 쓴다. 터미널에서는 "열린 질문에 2개 올렸습니다" 까지만
- **제안·할 일.** `할 일 목록` 섹션에 쓴다. 터미널에서 권하지 않는다

### 자기 점검 — 턴을 끝내기 전에

터미널에 쓴 문장을 하나씩 짚으면서 묻는다. **"이 문장이 가리키는 내용이 지금 캔버스 안에 있는가?"** 하나라도 없으면 터미널에서 지우는 게 아니라 **캔버스에 넣는다**. 터미널에만 있는 내용은 사용자에게 전달되지 않은 것으로 취급한다.

가장 흔한 사고는 캔버스를 다 고친 뒤 터미널 답변을 쓰면서 **그 자리에서 새 생각이 떠올라 거기에만 적는 것**이다. 떠올랐으면 캔버스로 돌아가 넣고, rev 를 다시 올린다.

## 할 일 목록 운영

사용자가 **직접 해야 하는 행동**은 설명 문단에 섞지 않고 `할 일 목록` 섹션에 모은다. 캔버스 맨 위에 고정돼 있고(`#content` 의 첫 섹션), 항목이 하나도 없으면 자동으로 숨는다.

### 무엇이 할 일인가

| 할 일 목록에 넣는다 | 넣지 않는다 |
| --- | --- |
| 사용자가 손으로 해야 하는 행동 (설정 변경, 링크 교체, 결정 내리기) | 내가 할 작업 — 그건 그냥 한다 |
| 기한·순서가 있는 실행 항목 | 사용자 답이 필요한 질문 → `한 눈에 보기` 의 `열린 질문` |
| 지금은 못 하지만 잊으면 안 되는 것 | 배경 설명, 판단 근거 → 해당 섹션 본문 |

판별 기준 하나다. **"사용자가 터미널을 떠나서 무언가 해야 하는가?"** 그렇다면 할 일이다.

### 마커와 마크업

```html
<!-- TODO -->
          <ul class="check">
            <li data-done><span class="what">링크드인 Featured 에 블로그 직접 링크 걸기</span></li>
            <li><span class="what">프로필 헤드라인을 새 카테고리 문장으로 교체</span>
                <span class="why">현재 문구는 구 카테고리 기준</span></li>
            <li data-blocked><span class="what">대문에 JSON-LD Person 추가</span>
                <span class="why">본명 노출 범위가 정해지면 착수</span></li>
          </ul>
<!-- /TODO -->
```

- `<span class="what">` 은 **완료 시 취소선이 걸리는 범위**다. 한 줄짜리여도 감싼다
- `<span class="why">` 는 한 줄 보조 설명(왜 / 막힌 이유 / 선행 조건). 없어도 된다
- 상태는 셋 — 미완(속성 없음) · `data-done`(완료) · `data-blocked`(막힘)
- 완료 개수(`3 / 7 완료`)는 제목 옆에 **자동 계산**된다. 숫자를 손으로 쓰지 않는다

### 상태를 항상 맞춘다

**매 턴, 할 일 목록을 먼저 본다.** 이게 할 일 목록 운영의 핵심이고, 빠뜨리면 목록이 거짓말을 시작한다.

| 이번 턴에 벌어진 일 | 할 일 목록에 할 것 |
| --- | --- |
| 사용자가 "했어", "걸었어" 라고 말함 | 그 항목에 `data-done` 을 붙인다 |
| 내가 대신 처리했다 | 그 항목에 `data-done` 을 붙인다 |
| 사용자 답·외부 조건 때문에 못 하게 됐다 | `data-blocked` + `<span class="why">` 에 막힌 이유 |
| 막혔던 조건이 풀렸다 | `data-blocked` 를 떼고 `why` 를 지운다 |
| 더 이상 할 필요가 없어졌다 | 항목을 **지운다**. 완료로 속이지 않는다 |
| 새 행동을 권하게 됐다 | 목록 맨 끝에 미완으로 추가한다 |

완료된 항목은 **지우지 않고 남겨 둔다** — 무엇을 이미 했는지가 다음 판단의 재료다. 다만 완료 항목이 미완보다 훨씬 많아져 목록이 읽기 어려워지면, 한 번 묶어 정리할지 사용자에게 묻는다.

## Step 1: 세션 시작

### 1-1. 캔버스 생성 + 브라우저 열기

Bash 한 번으로 끝난다. 제목은 `/talk-on-canvas` 인자에 있으면 그걸 쓰고, 없으면 지금까지의 대화 주제로 짧게 짓는다(예: `ascenthq 로그인 플로우 정리`).

```bash
for c in "${CLAUDE_PLUGIN_ROOT:-/nonexistent}/skills/talk-on-canvas/scripts/canvas.sh" \
         "${CLAUDE_CONFIG_DIR:-$HOME/.claude}/skills/talk-on-canvas/scripts/canvas.sh" \
         "$HOME/.claude/skills/talk-on-canvas/scripts/canvas.sh" \
         ".claude/skills/talk-on-canvas/scripts/canvas.sh"; do
  [ -f "$c" ] && { LC="$c"; break; }
done
bash "$LC" open "<제목>"
```

스크립트가 템플릿 복사 · 제목 치환 · 로컬 서버 기동 · 브라우저 열기를 전부 한다. 출력에서 `CANVAS=` 절대 경로를 받아 적어 두고, 이후 모든 Edit 은 그 경로에만 한다.

저장 경로를 사용자가 지정했으면 두 번째 인자로 넘긴다: `bash "$LC" open "<제목>" "<경로>"`. 기본값은 `~/claude-canvas/<날짜>-<슬러그>.html` 로, git 저장소 바깥이라 작업 트리를 더럽히지 않는다.

출력의 `MODE=` 가 알려주는 갱신 방식:

| MODE | 뜻 | 사용자 체감 |
| --- | --- | --- |
| `http` | 로컬 서버 기동 성공 | 1.2초마다 변경 감지 → 바뀐 부분만 교체. 깜빡임·스크롤 이동 없음 |
| `file` | python3 없음 또는 포트 실패 | 4초마다 통째 새로고침. 스크롤 위치는 복원됨 |

둘 다 사용자가 할 일은 없다. 새로고침을 누르라고 안내하지 말 것.

### 1-2. 지금까지의 대화를 백필

이 스킬은 보통 **대화 도중에** 호출된다. 빈 캔버스를 열어 놓고 다음 턴을 기다리지 않는다. 호출 직전까지의 대화를 훑어 아래를 바로 채운다.

- `한 눈에 보기` 4칸 — 지금 하는 일 / 다음 / 정해진 것 / 열린 질문
- 섹션 2~5개 — 지금까지 다룬 주제를 덩어리로 묶어서. 터미널에서 읽기 힘들었던 것(긴 표, 파일 목록, 비교, 단계별 계획, 코드)을 우선 옮긴다

대화가 거의 없는 상태(세션 첫 줄에서 호출)면 `한 눈에 보기` 의 `지금 하는 일`만 한 줄 채우고 섹션 없이 시작한다.

### 1-3. 사용자에게 안내

한 번만, 짧게.

```
캔버스를 열었습니다: <경로>
브라우저는 그대로 두세요 — 대화하는 동안 자동으로 갱신됩니다.
```

## Step 2: 매 턴 갱신 루프

캔버스가 열려 있는 동안 모든 턴은 이 순서로 끝난다.

**캔버스를 먼저 고치고, 터미널 답변은 마지막에 쓴다.** 순서가 뒤집히면 터미널에만 있는 내용이 반드시 생긴다.

1. **할 일 목록을 맞춘다** — 이번 턴에 완료·막힘·추가·삭제가 있었는지 먼저 본다. 변화가 없으면 건너뛴다.
2. **캔버스 본문을 고친다** — 아래 셋 중 해당하는 것만.
   - 이미 있는 주제 → 그 섹션을 Edit 으로 교체
   - 새 주제 → 섹션을 맨 끝에 추가
   - 상태가 변했으면 → `한 눈에 보기` 해당 칸 Edit
3. **rev 를 올린다** — `<html ... data-rev="N">` 을 N+1 로. 이번에 건드린 섹션들의 `data-rev` 도 같은 값으로 맞춘다. 이게 "방금 갱신" 표시와 목차 NEW 뱃지를 만든다.
4. **터미널에 포인터만 쓴다** — 2~4줄. 쓴 문장이 가리키는 내용이 전부 캔버스에 있는지 확인한다. 없으면 1번으로 돌아간다.

여기서 턴이 끝난다. 사용자가 다음 말을 하면 다시 돈다.

### 턴 종료 조건

**캔버스를 고치지 않고 끝내도 되는 턴은 셋뿐이다.**

- 사용자의 요청 자체가 캔버스 조작일 때 (그 조작이 곧 갱신이다)
- "응", "그렇게 해줘" 에 대한 한 문장 확인 응답
- 캔버스에 담을 내용이 전혀 없는 잡담

그 외 전부 — 조사 결과, 코드 수정, 의견, 비교, 실패 보고, 심지어 "안 됩니다" 한 줄짜리 결론까지 — 캔버스에 자리가 있다. **"안 됨"과 그 이유야말로 나중에 다시 찾게 되는 내용이다.**

### 무엇을 캔버스에 넣는가

터미널에서 읽기 나쁜 것부터. 이 순서대로 우선한다.

| 1순위 | 표 · 비교 · 파일 목록 · 수치 · 단계별 계획 · 코드/diff |
| 2순위 | 결정과 그 이유, 포기한 선택지와 그 이유 |
| 3순위 | 설명 산문 (길면 캔버스, 짧으면 터미널) |

**넣지 않는 것:** 도구 호출 로그, 사용자가 방금 한 말의 복창, 진행 중계("이제 파일을 읽겠습니다"), 캔버스 조작 자체에 대한 설명.

### 섹션을 어떻게 쪼개는가

정답은 없고 기준만 있다. **"사용자가 나중에 이 화면에서 뭘 찾을까"** 로 자른다.

- 한 섹션 = 한 질문에 대한 현재 답. 스크롤 1~2 화면을 넘기면 쪼갠다
- 제목은 내용을 지목하는 명사구로 — `조사 결과` 말고 `Vercel 배포가 멈춘 원인 3가지`
- 작업이 단계로 진행되면 체크리스트 섹션 하나를 만들어 계속 같은 섹션을 고친다. 단계마다 새 섹션을 만들지 않는다

## HTML 조작 사양

템플릿의 마커는 각각 파일에 **딱 한 번** 나타나므로 Edit 으로 정확히 겨냥된다.

```
<!-- TODO --> … <!-- /TODO -->         할 일 목록 (고정 섹션 #sec-todo, 캔버스 맨 위)
<!-- SECTIONS_INSERT -->   ← 섹션 삽입 지점 (첫 섹션은 이 바로 뒤)
<!-- ST:now --> … <!-- /ST:now -->     한 눈에 보기: 지금 하는 일
<!-- ST:next --> … <!-- /ST:next -->   한 눈에 보기: 다음
<!-- ST:done --> … <!-- /ST:done -->   한 눈에 보기: 정해진 것
<!-- ST:ask --> … <!-- /ST:ask -->     한 눈에 보기: 열린 질문
```

### rev 올리기

매 갱신의 첫 Edit.

```html
<html lang="ko" data-rev="7">   →   <html lang="ko" data-rev="8">
```

### 섹션 추가

마지막 `<!-- /SEC:… -->` 바로 다음 줄에 넣는다. 하나도 없으면 `<!-- SECTIONS_INSERT -->` 다음 줄. 섹션은 대화 순서대로 쌓이므로 앞에 끼워 넣지 않는다.

```html
<!-- SEC:deploy-failure -->
        <section class="card" id="sec-deploy-failure" data-rev="8">
          <h2>Vercel 배포가 멈춘 원인</h2>
          <p>…</p>
        </section>
<!-- /SEC:deploy-failure -->
```

`id` 는 `sec-` + 슬러그, 마커는 같은 슬러그. 중복되면 목차가 어긋나므로 이미 쓴 슬러그는 재사용하지 말고 그 섹션을 고친다.

### 섹션 수정

`<!-- SEC:x -->` 와 `<!-- /SEC:x -->` 사이만 교체하고 `data-rev` 를 새 값으로 올린다. 바뀐 부분만 고치는 작은 Edit 이 통째 교체보다 낫다.

### 「한 눈에 보기」 채우기

네 칸 모두 비워 두면 탭이 흐려진다. 칸 하나는 `<p>` 한 줄이거나 `<ul>` 3~5개 항목이면 충분하다. 길어지면 그건 섹션으로 갈 내용이다.

```html
<!-- ST:done -->
            <ul>
              <li>로그인은 공통 입구 하나로 합치기로 함</li>
              <li>당당 쪽은 당분간 스텁 유지</li>
            </ul>
<!-- /ST:done -->
```

- `지금 하는 일` — 한 줄. 매 턴 바뀔 수 있다
- `다음` — 확정된 다음 행동만. 추측은 쓰지 않는다
- `정해진 것` — 번복되기 전까지 남는다. 번복되면 지우고 새 결정을 쓴다
- `열린 질문` — 사용자 답이 필요한 것. 답을 받으면 지우고 `정해진 것` 으로 옮긴다

### 쓸 수 있는 블록

| 블록 | 마크업 |
| --- | --- |
| 본문 | `<p>` `<ul>` `<ol>` `<blockquote>` `<strong>` `<code>` |
| 소제목 | `<h3>` (섹션 안에서만. `<h2>` 는 섹션 제목 전용) |
| 표 | `<table><thead>…` — 좁은 화면에서 자동으로 가로 스크롤된다 |
| 코드 | `<pre><code>…</code></pre>`, 줄 단위 `<ins>`/`<del>` 로 diff 표현 |
| 키-값 | `<dl class="kv"><dt>키</dt><dd>값</dd></dl>` |
| 체크박스 목록 | `<ul class="check">` — **`<!-- TODO -->` 안에서만 쓴다.** 섹션 본문의 나열은 평범한 `<ul>` 로. 체크박스가 여기저기 흩어지면 어느 게 진짜 할 일인지 구분이 사라진다 |
| 콜아웃 | `<div class="note"><span class="tag">왜</span>…</div>` · `.note.warn` · `.note.ok` |

HTML 특수문자는 이스케이프한다 — 코드 블록 안의 `<`, `>`, `&` 를 그대로 쓰면 레이아웃이 깨진다.

## 세션 정리

사용자가 캔버스를 끝내겠다고 하면 서버를 내린다. 말이 없으면 그대로 둔다 — 터미널 세션이 끝나도 파일은 남고, 서버는 사용자가 로그아웃하거나 아래 명령을 칠 때까지 산다.

```bash
bash "$LC" stop "<캔버스 경로>"
```

## 흔한 실수

| 증상 | 원인 | 대응 |
| --- | --- | --- |
| 브라우저가 안 바뀐다 | `data-rev` 를 안 올렸다 | rev 를 올린다. http 모드는 rev 비교로만 갱신을 감지한다 |
| 섹션이 목차에 안 뜬다 | `class="card"` 누락 또는 `id` 중복 | 두 속성 모두 확인 |
| "방금 갱신" 이 안 붙는다 | 섹션 `data-rev` 와 `<html>` 의 rev 가 다르다 | 둘을 같은 값으로 맞춘다 |
| 캔버스가 터미널 로그처럼 길어진다 | 같은 주제에 섹션을 계속 쌓았다 | 기존 섹션을 고쳐 쓰는 방식으로 되돌린다 |
| Edit 이 마커를 못 찾는다 | 들여쓰기 불일치 | 그 Edit 만 다시. 파일 전체 재작성은 마지막 수단 |
| 터미널에만 있는 할 일이 생겼다 | 터미널 답변을 쓰면서 새로 떠올린 것을 거기 적었다 | `<!-- TODO -->` 에 넣고 rev 를 다시 올린다 |
| 할 일 목록이 안 보인다 | 항목이 0개면 자동으로 숨는다 | 정상 동작. 항목을 넣으면 나타난다 |
| 체크박스 줄의 글자가 세로로 쪼개진다 | `ul.check li` 를 `display: grid` 로 만들었다 — `<strong>` 같은 인라인 자식이 각각 grid 항목이 돼 좁은 칸에 끼인다 | `position: relative` + `padding-left` 로 되돌린다. 박스는 `::before` 를 absolute 로 띄운다 |
| 완료 개수가 안 맞는다 | 제목 옆 숫자는 자동 계산이다 | 손으로 쓴 숫자를 지우고 `data-done` 만 맞춘다 |

## 합리화 차단

| 떠오르는 생각 | 실제 |
| --- | --- |
| "이번엔 짧은 답이라 굳이 캔버스까지" | 짧은 답일수록 스크롤백에 묻힌다. `한 눈에 보기` 한 줄이라도 고친다 |
| "곧 또 바뀔 테니 나중에 몰아서" | 사용자는 지금 그 화면을 보고 있다. 중간 상태도 상태다 |
| "터미널에 이미 다 썼으니 됐다" | 사용자는 터미널을 안 읽는다. 터미널에만 있는 내용은 전달되지 않았다 |
| "이 정도는 터미널에 적어도 되겠지" | 그 한 줄이 양쪽 내용을 어긋나게 만든다. 예외는 없다 |
| "요약만 터미널에 보여주면 친절하다" | 같은 내용을 두 번 읽히는 것이다. 포인터만 남긴다 |
| "할 일이라기엔 사소하다" | 사용자가 손으로 해야 하면 할 일이다. 크기는 기준이 아니다 |
| "완료했는지 사용자가 알 테니 그대로 둔다" | 상태가 틀린 목록은 안 쓰는 목록이 된다. 매 턴 맞춘다 |
| "대화가 주제를 벗어났으니 캔버스 밖" | 섹션을 하나 더 열면 된다. 벗어난 대화도 작업이다 |
| "Edit 토큰이 아깝다" | 마커 Edit 하나는 20줄 안쪽이다. 안 고치면 스킬이 꺼진 것과 같다 |
| "실패/부정 결론은 적을 게 없다" | 안 되는 이유야말로 다시 찾게 되는 내용이다 |

**이 생각이 들면 전부 같은 뜻이다 — 지금 캔버스를 고쳐라.**

## 주의

- 로컬 서버는 `127.0.0.1` 에만 바인딩되고 캔버스가 있는 폴더를 서빙한다. 민감한 파일이 있는 폴더를 저장 경로로 지정하지 않는다.
- 캔버스 파일 옆에 `<파일명>.server` (pid·포트 기록) 가 생긴다. 서버를 내리면 지워진다.
- 캔버스를 git 저장소 안에 두면 작업 트리에 untracked 파일로 뜬다. 기본 경로(`~/claude-canvas/`)를 쓰면 이 문제가 없다.
- 캔버스 내용은 로컬 밖으로 나가지 않는다. 사용자가 Artifact 발행을 요청하면 그 내용이 Anthropic 서버에 올라간다는 점을 한 줄로 알리고 진행한다.
- 사용자가 브라우저 탭을 닫았다가 다시 열어도 URL 만 같으면 그대로 동작한다. URL 을 잊었으면 `CANVAS=` 경로를 다시 알려준다.
- UI 라벨은 한국어로 박혀 있다. 영어 세션이면 탭 버튼과 `한 눈에 보기` `<h3>` 문구를 Edit 으로 바꾼다.
